# OurPawmily — architecture summary (for independent review)

A read-only overview of how the app is built, as of October 2026 (beta, two active users).
It describes the code in this repository; it contains no secrets, keys, tokens or family data.
Line numbers are approximate; function names are the stable reference.

## 2. Technology stack

- **Frontend:** plain HTML/CSS and native ES modules — no framework, no bundler, no npm runtime dependencies. Lazy `import()` for feature logic. A service worker (`sw.js`) caches the trackers' shell (network-first). Cache-busting via `?v=` on `family/app.js` and `style.css`.
- **Backend:** one Cloudflare Worker (JavaScript, ES modules). Storage: **Workers KV** (binding `HOUSEHOLD`; v2 keys are prefixed `v2:` through `store()` in `server/family.js`; Home's lists are `requests:<fid>` and `groceries:<fid>`), **R2** (binding `PHOTOS`, encrypted photo files), the **Cache API** (`caches.default`) for TMDB lookups.
- **Server dependency:** `@anthropic-ai/sdk` only (`server/package.json`), loaded with dynamic `import()` when a Claude call is made. Gemini is called with `fetch` (REST).
- **Tests:** Node's built-in `node:test`; browser checks with Playwright in CI (`scripts/check-links.mjs`) and during development.

## 3. Hosting and Cloudflare architecture

- **Static site:** GitHub Pages serves the repository (`APP_ORIGIN` in `server/wrangler.toml`). It is not Cloudflare Pages.
- **Worker** (`server/worker.js`): `fetch` handles
  - `/v2/*` → `familyApi()` in `server/family.js` (everything in OurPawmily);
  - legacy tracker endpoints: `/household/<code>/…` (data, calendar `.ics`, files), `/ics` (calendar proxy), `/assistant` (workout "Ask Claude"), WHOOP and Strava OAuth (`/whoop/*`, `/strava/*`; Strava is no longer offered for new connections). `/v2/config` reports which device connections are set up (only whether, never keys).
- **Crons** (`wrangler.toml`, dispatched in `worker.js scheduled()`):
  - `13 10 * * *`: nightly maintenance (`runMaintenance`).
  - `*/15 * * * *`: reminders and pushes (`runReminders` in `push.js`); at 6:45/15:45 Pacific also the news edition (`news.js`), but only when the `NEWS_ON` var is set — news is hidden in 2.0 (code and stored editions kept).
  - `13 13-22 * * 3`: Wednesday date scout, one area per run (`runScout`).
  - `43 13-22 * * 4`: Thursday refresh (no AI).
- **Durable Object** `ChatHub` (`server/chatHub.js`, SQLite-backed, free plan; bound as `CHAT`): one per family (`idFromName(fid)`). It stores that family's chat messages (sealed) and holds the phones' WebSockets (hibernation API, `ping`/`pong` auto-response). The Worker authenticates every chat request in `chatRoutes()` (`server/chat.js`) and passes the caller's member ID, their allowed chats and the family's current grown-ups to `POST /op`; sockets connect at `/v2/chat/ws` with a one-time ticket (60 s, single use, stored in the object) and an `Origin` check, and are closed when their member leaves or stops being eligible. The demo runs the same `ChatCore` over its local store.
- **R2:** photos are stored as `photoKey(fid, id, size)` (`server/photos.js`), `full` and `thumb`, already encrypted on the phone; served with `Cache-Control: private, immutable`. A per-family quota (`quotaBytes`) is enforced on upload.
- **Free-plan constraints the code is written around:** ≤ 50 outside requests per invocation (scout one area per run, link checks capped, news ≈ 20), few KV writes (one shared news record, background-job results with 1-day TTL), Cache API for repeated lookups.

## 4. Authentication and authorization

1. **Google sign-in** (Google Identity Services in the browser) → `POST /v2/auth/google` with the ID token.
2. `verifyGoogle()` (`server/family.js`) checks the RS256 signature against Google's certs (cached 1 h), issuer, audience (`GOOGLE_CLIENT_ID`), expiry, `email_verified` (must be `true`; a missing claim is refused) and `iat` (a token issued in the future is refused).
3. `startSession()` issues a random session token (stored in KV as `session:<token>`, 30-day TTL; the newest 10 per account are listed in the user record for "sign out everywhere"). The phone keeps it and sends `Authorization: Bearer …`.
4. **Authorization** is by membership: `loadFamily()`/`meIn()` only return a family whose `members[]` includes the caller's account ID (`g<google sub>`). Roles: `owner` (settings, delete, hand-over), `member`, and `relation: child` (restricted writes; no chats). Chats (`grownUp()` in `server/chat.js`) require an account, `relation !== 'child'`, and no birthday under 18. Friends' families are linked through `connections[]` and only see posts and threads shared with connections. **Files** (`server/photos.js`): each upload records its uploader (`fileby:<fid>:<pid>`); only the uploader or the family's creator can replace or delete it; posts, thread screenshots/PDFs, albums, chat messages and market listings accept only files the caller uploaded; a connected family fetches a file only by naming the shared post or thread it's on, never one tagging a member the family keeps private, and nothing after disconnecting. **Report/block** exist on threads and replies (report hides it for the reporter; the creator sees a count) and chat messages (the report keeps the message ID and reason, never the sealed content); blocking hides threads, replies and chats from that account.
5. **Invites** (`makeInvite`, `/invites/:code(/accept)`): single-use, 14-day TTL, bound to one email; accepting requires the signed-in Google email to equal the invite's email, then the account ID is bound to the member spot.
5b. **Leaving / deleting:** `removeMember(…, { keepPosts: false })` (leaving a family, deleting an account) deletes the person's tracker data, chats, posts and comments, their 🙋 requests (and unclaims ones they'd taken), and their threads (with screenshots, PDFs, uploader records and reports) and replies, votes, tags, reads and follows (`scrubThreads`). `deleteFamily` deletes every thread and uploader record with the family's files.
6. **Admin**: `ADMIN_EMAILS` secret; the maintainer desk (`/admin/*`).
7. **Demo mode**: `family/api.js` runs `familyApi` in the browser with a localStorage store; `/auth/demo` exists only when `env.DEMO` is set.
8. **Legacy trackers** authenticate with a **household code** (a shared secret in the URL path). The code is no longer shown, typed or sent anywhere in the UI (no Privacy card, no "Link phones", no `#link=`, no calendar subscribe link); phones that already shared through one keep syncing in the background until migration, and 🛟 Recover reads the old copies. "Just the trackers" sharing without an account is retired: sharing is only through a family. The endpoints remain.

## 5. End-to-end encryption and key management

Implemented in `family/crypto.js`; used throughout `family/app.js`.

- **Cipher:** AES-256-GCM via WebCrypto, 12-byte random IV, output `e1:<base64url(iv‖ciphertext)>` (`seal`/`open`/`tryOpen`; `sealBytes`/`openBytes` for photos).
- **Family key:** 32 random bytes from `newKey()`, created on the phone in `encryptFamily()` (`app.js`) when a family is created. The server gets only a **key check** (a constant sealed with the key) to tell right keys from wrong ones (`makeCheck`/`checkKey`).
- **On the device:** IndexedDB `pawmily-keys` (fallback localStorage `fam.keys`), loaded and validated in `loadKeys()`.
- **Getting the key to another device or person:**
  - Invite links: `inviteSheet()` appends the family key (or a connection key) after `#` in the URL.
  - "Add a device": `deviceLink()` puts `#k=<fid>.<key>` after `#`.
  - Fragments are never sent to servers; `boot()` removes them from the address bar.
- **Recovery:** a 5×5-character recovery phrase (~124 bits) → PBKDF2-SHA-256 (310,000 iterations) → AES-GCM over `{fid: key}`; the locked backup is stored on the server (`lockBackup`/`unlockBackup`, `/account/keybackup`).
- **Friends' families:** each connection has a connection key, stored on the server sealed with each family's key (`connkeys`). A post shared with friends gets its own key `pk`, sealed for the family and for each connection.
- **📚 Read** (Phase 4 amendment): shared rules in `js/books.js` (book model, `normalizeState`, `parseSeries`/`seriesKey`, `genresOf`, `usPreview`, `lists`, per-member `signals`, `REASONS`/`reasonsFor`/`explain`, `bookRef`); server `server/books.js`; UI `family/read.js` (lazy). One KV record `books:<fid>` = `{ books: [{ id, by, at, body (sealed book details), aud: 'us'|'me'|'family', to: [memberIds] }], state: { bookId: { memberId: { s: want|reading|finished|dropped, f: read|listen|both, p?: {pct|page|ch|min}, r?, svc?, start?, done?, at } } } }` — titles only inside sealed bodies. Routes: `GET/POST /families/:fid/books`, `PATCH|DELETE /families/:fid/books/:id`, `PUT /families/:fid/books/:id/me` (your own state only; `state: null` takes it off your list), `GET /books/search?q=` and `GET /books/work/OL…W` (signed in, 40/min, Cloudflare cache 1 / 7 days), `GET /books/cover/<id>-S|M.jpg` (no sign-in — an `<img>`; numeric ids and two sizes only; cached 30 days). Visibility: `us` = the adder + their partner (`isCouple`) + anyone who later puts it on their list; `me` = only the adder; `family` = everyone. The audience can change only while nobody but the requester has state on the book (409 otherwise), so nobody's status is ever shown to a different group than when they added it. Only state of people who can see the book is returned. Delete: adder only, and only when nobody else has state. Leaving removes the member's state (and their `me` books); deleting the family removes `books:<fid>`. Discuss uses thread `ref: b:<bookId>` (one thread per book). Client dedupes by Open Library work id, else title + first author (`sameBook`). No book data existed before, so nothing was migrated.
- **Watch states** (`js/showsCore.js`): stored statuses are unchanged — `want` (new) and `upnext` show as *Want to Watch* (`upnext` = ⭐ Up Next), `watching`, `finished` (*Watched*), `dropped`. A record with no status keeps its old meaning (show → Watching, movie → Watched). `PATCH /watch/shows/:id {status, progress, night}` logs an episode in one call; `night` never removes an existing night.
- **🏋️ Workouts** (2.0 Phase 7): one model, `js/workout.js` (Workout → blocks (straight / superset / circuit, rounds) → items → one set per round with reps, weight + unit, bodyweight, time, distance, done/`got`, and `uncertain` field lists). Built by hand, from text (Phase 8) or a photo (Phase 9) — always this shape. Stored per person as two sealed records, `workouts:<fid>:<member>:today` ({today, templates}) and `:log` ({log}), via `GET/PUT /families/:fid/members/:id/workouts/today|log` — PUT by the person (with `base`: an older copy is refused, 409); GET by the person and their Fitness sharing list. Older lifting sessions and device workouts are read through adapters, never rewritten. UI: `family/fitness.js` (lazy); saves are batched (1.2 s) and flushed when the app goes to the background. Flow (H5): Add Workout → Today's Workout (`view: 'today'`, the plan) → Start Workout (`status: 'active'`, `startedAt`) → Train (`view: 'train'`; `logSet` keeps the plan in the set and the actual in `got`) → Complete (`complete` → `:log`). Items may be `perSide`; `W.progress` (exercises done, next set), `W.estMinutes`, `W.suggestName` (used when the title is untitled) and `W.isStrength` (history shows strength/circuit work; other device activity is one counted line, still in `workoutHistory` and still in Diet calories). An active workout is also backed up on the phone as `localStorage['fam.fx.active.<fid>.<member>']` = `{at, data}` (sealed with the family key in an encrypted family) and restored on load when newer than the saved copy and not already in the log; removed on complete/remove. The lifting program (`js/lifting.js`) is an input, not a second model: `js/programWorkout.js` makes the next program day a normal workout (`source: 'program'`, `program: {block, day, week}`, items carry `ref` = exercise id); finished program workouts are read back as lift sessions for `suggestLoad` / `blockPosition`. "Set up a lifting program" sets `lift.on` in the trackers (Fitness part). Signed in, the trackers' lifting logger is hidden (its tab is "Activity") and `lift.sessions` stays as history.
- **👔 Look** (Look MVP, `v2/look-mvp`): a secondary screen `family/#look` (not a bottom tab; `#fitcheck=<id>` opens a Fit Check), lazy `family/look.js` with the pure engine `js/look.js` and on-phone background removal `js/cutout.js`.
  - **Storage:** one sealed record per person, `look:<fid>:<member>` = `{savedAt, data: {v, items, looks, wears, prefs, ob, fc}}` via `GET/PUT /families/:fid/members/:id/look` (owner only — anyone else gets 404; `base` → 409 on a stale copy). Pictures via `GET/PUT/DELETE /families/:fid/members/:id/look/img/:imgId?size=thumb|full` (owner only), R2 keys `f/<fid>/look/<member>/<imgId>-thumb|full` (sealed bytes in an encrypted family; outside the reach of `/photos/:id`, which only builds `f/<fid>/<id>-…`; counted in the family's photo space; deleted with the family). Per-person picture count `lookimgs:<fid>:<member>` (900 max). Pieces: transparent WebP (PNG where WebP can't be encoded) at ≤ 360 px (grids, boards) and ≤ 1100 px (hero, Fit Check); outfit photos JPEG 560 / 1600 px. Grids load thumbnails only, lazily (IntersectionObserver).
  - **Fit Check:** `fitchecks:<fid>` list (14 days, both people still members): `POST /families/:fid/fitchecks` `{kind: one|ab, names: [sealed], msg: sealed}` → draft to the requester's partner (`partnerOf` + `isCouple`); `PUT …/:id/img/0|1` (requester, draft only) the board JPEG drawn on the phone (sealed); `POST …/:id/send` (notify, kind `us`, no Look details in the push); `POST …/:id/answer` `{verdict: hit|miss|a|b|neither, reasons}` (recipient only); `GET …` and `GET …/img/n` for the two of them only; `DELETE` by the requester. Which Look(s) a check was about stays in the requester's own record (`fc`).
  - **Recommendations, on the phone:** `dayContext` (the day's events → the most dressed-up occasion, a short label only) + `weatherNeed` (dress.js `whereOn`/`dressFor`, Open-Meteo cached in `fam.dressWx`) + `recommend` (Saved Looks incl. photo-only ones, plus every mix of the best few pieces per kind; score = formality fit, warmth, rain, colour rules, recent wear, learnt prefs, saved/hit bonus; Top 3 differing by ≥ 2 pieces where possible) + `reasonFor` (one line). `learn` keeps `prefs.item`, `prefs.pair`, `prefs.occ` bounded in [-3, 3] (occasion shifts ±1.5). ~12 ms for 120 pieces (test).
  - **Calendar / Home:** Calendar's old Dress for today (`renderCalDress`) is replaced by `renderCalLook` → `L.calendarCard` (today only; someone who never opened Look gets a static one-line card and nothing loads). Home's `homeLook()` reads `localStorage['fam.look.<fid>.<member>']` (date, label, count, worn name) — no request, no pictures.
- **🔀 Combining two copies of your trackers** (`js/account.js` `mergeData`, on `pull()` when another device saved since): fields and lists from both are kept, except a day's food, which is one record — `custom` (today's meal changes), `eaten` (what was logged), each `planned[date]` and each `dailyMeals[meal]` are taken whole from the later day, or on the same day from the winning (newer) copy. Blending them field by field kept an old meal's title and foods next to the new ones (a bar plus the chicken said in Talk) and brought back meals taken off (fixed 2026-11-02). Planning a meal that was already logged (Talk "Plan …", Tell me › Plan it) also takes it off the log.
- **✏️ Writing the trackers from the family app** (`editMine` in `family/app.js`): `account.connect()` → `account.pull()` (must have pulled once) → change `profileStore(owner)` → `account.push()` → clear the shared cache. Refused before any change when an encrypted family has no key on the device. Used by the 💪 Health weigh-in (`weights`) and the program setup (`lift.on`). The Health weigh-in is confirmed first in lazy `family/weighin.js` (`confirm` / `photosOnly`, pure `changeLine` / `posesFor`), which also saves progress photos through `js/photos.js` `savePhotos(owner, [{file, pose}], date)` into the phone's own IndexedDB (`ourpawmily-photos`, owner = `lp.g.owner`) — the same on-phone store as Food › Weight, never synced or uploaded. The opt-in morning weigh-in reminder is the `weighin` entry in `nudges:<uid>` (`server/nudges.js`, `{every: 1, last}` — a date, never a weight), sent by the 15-minute reminder run at 7 AM local with no numbers in it; a Health weigh-in posts `/account/nudges/weighin/done`.
- **🗣️ Talk, read on the phone only** (`js/talkParse.js`, before `parseTalk`; not steps, so `DOS` and the server's `TALK_SCHEMA` are unchanged): `photoAsk(text, hour)` → `{kind: 'meal', meal}` / `{kind: 'workout'}` shows a card whose 📷 / 🖼 buttons are the file inputs themselves (`capture="environment"` for the camera — iOS opens it only for a tap on the input); the file goes to `meals.js` `talkPhoto(meal, file)` (`photoSheet(meal, 'restaurant')` → `/ai/diet/photo`) or `fitness.js` `photoWith(file)` (→ `/ai/workout` → the editor). `howAsk(text)` → `{topic}` shows the ways to log a meal / workout / weight (`data-talkex` fills the box, `data-talksay` sends, `data-talk="healthopen|fitopen"`).
- **🍽 One food day** (`js/dayPlan.js`, pure; Health 2): targets (`baseTargetsOf` / `targetsOf`), the day's plan (`planOf` = `planForDay` over today's edits and daily meals), the log (`logOf`), totals with alcohol apart (`consumedOf`, `drinkEntry`: alcohol kcal = kcal − 4·carbs), the `days[date]` summary (`dayEntry`, now with `alc` and `complete`), and changes on a store (`rollDay`, `logPlanned`, `logAs` — a non-plan meal becomes today's custom meal so `planForDay` re-fits the meals still to come — `addExtras`, `setGrams`, `setDone`, `lockAmount`, `setPick` — 🔁 a slot's food from its own options, today's `custom.meals[meal].picks` plus `prefs[key][slot]` except lunch/dinner proteins, the trackers' rule). **Sticky amounts:** `prefs.locks[key][slot] = {food, grams}` (key: the breakfast template, or `main` for lunch and dinner; `null` once unlocked, so an older copy can't bring it back) is applied by `stickyGrams` (`js/plan.js`) inside `planForDay`'s `merge`, only while the slot's food is the locked one; a day's own grams still win. `prefs` sits in the diet part, so it syncs like picks. A logged meal's snapshot carries `ts` (ms) as well as `at` (display); Health's food anchor (`foodState` in `family/health.js`) shows `just` — the meal logged in the last hour, with its P · C · F — until the next meal's window (`MEAL_HOURS`), and the next meal's planned macros (`macros`). **⚖️ Fit to N kcal** (`js/mealFit.js`): `fitMacros` sets the aim — protein in grams (the meal's plan, ≤ ½ of N, ≥ `perMealProtein` = 0.4 g/kg unless that is > 60 %), carbs : fat in the plan's ratio — and `fitPortions` solves the grams by weighted least squares (kcal, protein shortfall, carbs, fat) with low-calorie veg fixed, monotone bounds (down never grows a food, up never shrinks one), slider steps and ranges, and 🔒 locks; What's left passes the day's remaining macros as `aim`. Used by Health's meal sheet and the trackers' Fit. The trackers (`js/app.js`) and Health both use it; `whatFits` ranks planned meals, combos, packaged and recent meals (protein-first when calories are used up) on the phone.
- **📈 Plan progress** (`js/planProgress.js`, pure, on the phone): week / days left from `profile.phaseStart` (else `createdOn`) and `phaseWeeks`; status from the 21-day least-squares trend of this phase's weigh-ins vs the planned rate from `dailyTargets` (tolerance max(0.3, 35%)); "too early" when < 5 weigh-ins, < 10 days, a > 7-day gap with < 8 points, or a trend > 3 lb/wk or > 1.5% of body weight per week; maintenance/break target 0, gain inverted; goal-date estimate only for cut/gain with a goal, worded as an estimate. Never writes anything. Shown above Meals (trackers) and as one line on 💪 Health (`family/health.js` `dietSummary().progress`; `nudgeFor` picks the day's calm line).
- **🔑 Household areas** (2.0 Phase 6): `member.access` ⊆ `home | calendar | threads` (absent = all; the creator always all), set only by the creator (`PATCH /members/:id {access}`, or `access` when the creator adds a person). One guard in `familyApi` maps the first segment after `/families/:fid/` to an area (`AREA_OF`: home, requests, groceries, chores, care, appts, dogstats, vaxdue, tidy → home; events, calfeeds → calendar; threads, boards, albums → threads) and answers 403. `threads.js` applies Threads to the cross-family list, connected-family threads (`threadFamilies`), and tagging; `sharedFile` requires Threads in the family that reaches a connected family's thread file; request notifications skip people without Home. Not gated: Us (couple), Health (per person), chats (grown-ups), games, the file store as such (in-family file ids are only handed out through resources a member can see).
- **💪 Health parts** (`js/healthParts.js`): a person's tracker copy (`data:<fid>:<member>`, sealed) is also saved by their own phone as three sealed parts, `health:<fid>:<member>:diet|fitness|us`, each sent only when it changed (`account.pushParts` in the trackers, `saveMine` in the family app). `GET/PUT /families/:fid/members/:id/health/:part`: PUT by the person only (or the person who added someone not yet joined); GET Diet/Fitness by the person and the members in their `share.diet` / `share.fitness` lists (set only by that person; an older single `shareWith` counts for both until either is set), Us by the person's partner only (`canSeePart`). Once any part exists (`member.healthSplit`), the full copy is the person's alone; before that, a member in both lists can still read it (the pre-2.0 behaviour). Linked calendar addresses, device sign-ins and per-phone bookkeeping are in no part. Leaving a family or deleting it deletes the parts.

## 6. AI integrations and data flows

Keys are never sent to any AI provider. All calls happen on the Worker; none run on the phone.

**The AI privacy gateway (`server/aiGateway.js`, 2.0 Phase 8).** Every request carrying personal content goes through `aiCall({ db, purpose, input, who, underLimit }, run)`: the purpose must be one listed in `PURPOSES`; `minimize()` keeps only that purpose's allowed fields, each with a size cap (over the cap → 413), and names the dropped ones; the provider must be the purpose's own, and `personal-text` / `personal-image` payloads may only go to Anthropic (`public` may also go to Gemini); an optional per-person daily cap (`ai:<purpose>:<uid>:<day>`); and an audit record per call (`aiaudit:<day>:<id>`, 30-day TTL) with purpose, provider, payload kind, allowed field names, sizes, the number of dropped fields, ok/error status and duration — never values or caller-chosen names. Every purpose has a per-person daily cap (`ai:<purpose>:<uid>:<day>`). `run(payload)` receives only the minimized payload. Purposes: `workout.text`, `workout.photo`, `outing.plan`, `outing.swap`, `thread.tidy`, `tracker.command`, `help.chat`, `bingo.squares`, `look.item`, `look.pieces`, `diet.photo`, `diet.text`, `diet.coach`, `talk.route`, `talk.day`. ## 9. Known limitations and open items

Security items previously under review — all **FIXED in 2.0 Phase 0**:
1. **Connected-family photo access — FIXED:** files record their uploader; a connected family can fetch a file only by naming the shared post or thread it's on (never one tagging a privately kept member, nothing after disconnecting), and only the uploader or the creator can replace or delete it.
2. **`email_verified` — FIXED:** `verifyGoogle()` now requires `email_verified` to be `true` (a missing claim is refused) and refuses tokens issued in the future.
3. **Outing text → Gemini free tier — FIXED:** 🧭 outings and swapping a stop go to Claude only, never Gemini.

**FUTURE SECURITY PROJECT: Per-person/per-area cryptographic isolation for Diet and Fitness.** Today every family member holds the same family key, so Family membership permissions (household areas, Diet/Fitness sharing) are enforced by the server, not cryptographically isolated between family members. Acceptable for the beta; before a commercial or external-family launch this will be separately designed and audited (whether personal Health areas need separate encryption keys). Not part of Phase 0 or 1; the key architecture is unchanged.

**Day-planning boundary (Health 2 Phase B; the assistant itself is FUTURE, not built).** A future "Talk to Pawmily" command layer may combine WHOOP context, calendar, workout duration, schedule feasibility, routing/traffic, Watch, Read, Dates and household responsibilities to *propose* plans and actions (design: `docs/TALK_TO_PAWMILY.md`; T0 adds `js/talkActions.js` — the action registry, step/plan checks, the shared-person rule, name→role tokens and per-lookup fact allowlists — as tested code that nothing calls yet). Because domain records are sealed on the phone, its executor would run on the phone and apply approved steps through each domain's existing write path. No subsystem owns that orchestration, and none is built. Each subsystem exposes a narrow read-only or preview-first interface instead: Fitness — `W.proposeVariant(workout, intent)` in `js/workout.js` (intents `lighter`, `shorter`; returns a today-only copy plus a change list for a preview; never saves, never touches saved workouts) and `W.durationFor(workout, history)` (your usual time for that workout, else the estimate); WHOOP — `dayContextForPlanning({ daily, today, workout, history })` in `js/whoopDay.js` (structured facts only: recovery state / band / relative to usual, sleep hours / need / deficit, strain yesterday / today, the planned workout's id, name, estimated minutes and status; privacy boundary unit-tested; no caller yet, never sent to Claude in Phase B). WHOOP supplies context; it never changes the training plan by itself.

Household-code migration (open): since 2.0 Phase 2 no code is created, joined or changed (`sync.ensure`, `join`, `rotate` removed), and signed-in phones store dog documents and adoption photos in the family file store (`account.putFile` → `/v2/families/:fid/photos/:id?size=doc`, sealed with the family key). The remaining dependencies are listed in `tests/dependencies.test.js` — existing phones' background sync, reading files shared earlier under a code, the old calendar subscription link, 🛟 Recover's old copies, linked calendars in the trackers, and the legacy assistant route . **2.0 Phase 10:** a signed-in phone never uploads to the code (`sync.household()` is false once `account.active()`), so the per-part sharing choices are the only way trackers reach anyone; it still reads a partner who hasn't moved (`householdReads()`), never one whose trackers are on their account in the family (`movedToAccount`). Dog files read from the code are copied into the family file store (`account.putFile`) on first open; trackers' linked calendars refresh through `/v2/ics` (`account.ics`). Still on the code: phones that aren't signed in (read and write, unchanged), 🛟 Recover's reads, the legacy assistant route for them, and the old copies themselves (not deleted — a decision for later, see BUILD_PROGRESS).

Design items deferred to the security redesign:
- **Invite and device links carry the key**, so the key ends up in email and messaging histories.
- **No key rotation** when a member is removed.
- **Invite keys are left in localStorage** (`fam.inviteKey`/`fam.inviteCk`) if an invite is declined or has expired.
- **Session tokens are stored unhashed** in KV.
- **Keys are kept as extractable strings**, and the session token is in localStorage, so an XSS would expose both.
- **Legacy household-code endpoints** remain (hidden from the UI), with older plaintext tracker copies, until the Phase 2/10 migration.
- **500 responses return `err.message`.**
- **Decrypted photos are cached on the phone** (IndexedDB `photoDb`) with no expiry, and they stay after leaving a family.

## 10. Performance notes and likely bottlenecks

- **No build step:** `family/app.js` is ~442 KB unminified (plus `style.css` ~103 KB), parsed on every cold start. Feature logic and the 2.0 screens are lazy-loaded: 💪 Health (`health.js`), 🏋️ Fitness (`fitness.js` with `js/workout.js`, `js/workoutText.js` only when Describe it is used), ⌚ Devices (`deviceScreen.js` + `js/devices.js`) and 📺 Watch (`watch.js`, moved out of `app.js` in the final review: start-up script 182 → 176 KB). Lazy modules get the helpers they need from `app.js` once (`init`).
- **Home** (2.0 Phase 3): one `GET /families/:fid/home` returns both 🙋 requests and 🛒 groceries (two KV reads). Start-up is 14 API requests on the synthetic family; the dogs' profiles and stats load only when *More about the dogs* is opened, the vaccine due dates are re-checked once a day per phone 8 s after start-up (for the 9 AM reminders), and Home re-reads `/threads` and `/us` at most every 2 minutes (the app refreshes them when it comes back to the foreground). The Needs-you and Groceries cards keep their last height on the phone (a number only) so the page doesn't jump while they load.
- **🔄 Fresh shared files** (2026-11-07): `scripts/bump-version.mjs` also writes an import map into `family/index.html` (`<script type="importmap" id="versions">`) mapping every `../js/*.js` to `?v=<version>`, and puts its exact `'sha256-…'` hash into that page's `script-src` (the page allows no other inline script). Before this, OurPawmily's lazy screens imported shared files such as `js/foodText.js` at a fixed address, so after an update a phone could run a new `meals.js` with an old cached food reader (seen with the chicken-noodle-soup fix). `tests/versions.test.js` checks the map covers every file and the hash matches.
- **🐾 Opening** (2026-11-03): markup in `family/index.html` (`#splash`, the icon's paw as inline SVG, letters as spans — no font file, no image, no script of its own; CSP unchanged), CSS in `family/style.css` (`.splash`, transform/opacity keyframes only; a 6 s self-lift if the app never says it's ready). `theme.js` adds `nosplash` to `<html>` for a reload, back/forward, or a page of this app as referrer (coming back from the trackers), so it plays on cold launches only. `family/app.js` `splashDone()` runs when `boot()` settles and lifts it no earlier than `SPLASH_MS` (3 × 1.28 s, matching the CSS `--sp-t: 3` slow-mo the owner chose; 0.3 s with Reduce Motion), and a tap lifts it at once (`liftSplash`, a 0.25 s fade); the element is then removed. The 6 s self-lift became 10 s. The manifest's `background_color` is the icon green so Android's launch screen leads into it.   - **Shared requests** (`family/shared.js`, in memory only, gone when the app closes): one request per path at a time, reused for 20 s. It fetches what Health (`memberData`, `fit()`) and Us (`/ideas`, `/watch`, the partner's `us` part) read first.
